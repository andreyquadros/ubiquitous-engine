### Deviations from the design

- **Two `CHECK` constraints on `nofap_sites`** that 7.3 does not have: `origin = 'user' OR host IS NULL` and `length(host_key) = 16`. "A learned site is its hash only" is then a property of the file, not only of the code that writes it. A future origin that needs a name needs a migration.
- **`upsert_site` drops the name of a site that is not the user's.** A `Learned` or `Snooze` row is written with `host = NULL` whatever the caller passed, so the row read back differs from the one passed in that field. The reference keeps what it is given. Reason: the name must not reach the file by a caller's mistake.
- **`bump_day` validates.** A day that is not a canonical `YYYY-MM-DD` calendar day, or an hour above 23, is `CoreError::Invalid` and nothing is written. The reference accepts anything. Reason: retention compares days as text, and one malformed day would never be pruned or would be pruned at once.
- **Lenient reads go further than `nofap_day.kind`.** `days_between` also skips a row whose hour is not 0..=23 and clamps a count outside `u32`. `list_sites` skips a row whose `list` or `origin` this build does not know. `totals_by_kind` leaves out an `ai_usage.kind` it does not know (so the split can add up to less than `totals`).
- **`erase_history` overwrites what it frees.** It runs with `PRAGMA secure_delete` on and then `wal_checkpoint(TRUNCATE)`, and restores the connection's setting. The design says "deleted"; without this the counters and the snooze hashes stay readable in the file and in the log until the pages are reused. `delete_site`, `delete_sites_by_origin`, `purge_expired_sites` and `delete_days_before` are plain deletes.
- **`delete_for_block` does two things more** than the port's sentence: it also deletes the screenshot the block itself points at (`blocks.screenshot_id`), and it sets that pointer to NULL, in one transaction.
- **The error for an unreadable configuration names the place, not the content.** serde's message quotes the offending value, which can be a host from a pending change; the repository reports the error class, line and column only (`CoreError::Storage`).
- **`parse_explicit` is stricter than "invalid JSON or an unknown verdict".** An unknown confidence, a missing or extra field, a duplicated field, a different letter case, text around the object or a Markdown fence are all `UNSURE` (`unsure`, `low`, not refused). Only surrounding whitespace is tolerated.
- **Two truncations are an error**, `CoreError::Ai("screen check answer truncated twice")`, not `Unsure`. The design only says "one retry at 256". A model that cannot answer in 256 tokens will never answer, and the service's health tracking should see that instead of paying for an endless run of "unsure".
- **A blank model id is `CoreError::Invalid`** before any call. The vision classifier falls back to the default Anthropic model, which would be wrong for another provider.
- **The truncation warning is skipped too** for `NofapVision`, besides the three lines the design names (it is on the success path and carried the kind).
- **A content refusal over HTTP 400 is a refusal.** For OpenAI-compatible vendors, a 400 whose error code is `content_policy_violation`, `invalid_prompt` or `content_filter` is now `CoreError::AiRefused` (it was `Invalid`), for every kind of call, and the retry loop writes no line for it; kinds other than `NofapVision` get one warn line from the client. Not in the design. Reason: the old failure line carried the vendor's "rejected by our safety system" text with a timestamp, which for a screen check is a log of the screens a provider declined. **The three codes are from my knowledge of the vendors' documentation and were not observed against a live API.** If they are wrong the mapping never fires and the old behaviour remains.
- **`redact_images` is generic**, not two special cases: it replaces the `data` of any `{"type": "base64"}` object and any `data:…;base64,` string anywhere in the body.
- **Proxy: the 413 is Anthropic-shaped** (`request_too_large`), where the framework's own rejection is plain text. The module's rule is that every error has that shape. The licence is still checked before the size.
- **The test of the prompt reads `docs/nofap/DESIGN.md`** (`explicit::tests::the_prompt_and_the_schema_are_the_design_documents`) and compares the constant and the schema with the fenced blocks of 4.5. If the document moves or those blocks are reformatted, that test fails and has to be pointed at the new place.

### Contract notes for other units

**U5 (engine service)**

- `SqliteStore` implements `NofapRepo`. `load_config` returns the default only when the row is missing, and `Err(CoreError::Storage)` for a row that does not parse (integrator decision 10). **It does not call `sanitize()`, and neither does `save_config`**: the reference does not, so the service has to, after every load and before every save.
- A user site round-trips with its name. A learned site or a snooze comes back with `host: None` even if it was passed with one.
- `list_sites` is in insertion order; a replaced row moves to the end, as in the reference. `upsert_site` replaces by id and by `(list, host_key)`, so one upsert can displace two rows.
- `purge_expired_sites(now)` deletes every row with `expires_at <= now`, whatever its origin, as the reference does. Times are stored in milliseconds.
- `bump_day` needs a real day and an hour 0..=23, and saturates at `u32::MAX`. `days_between` is inclusive and ordered by day, hour and the kind's string. `delete_days_before(day)` keeps `day` itself.
- `erase_history` deletes the counters and the snoozes only. Clearing `values` and `plans` (7.4) is a configuration change the service makes.
- `wipe_user_data` deletes `nofap_day` and every `ai_usage` row and keeps `nofap_state` and `nofap_sites`, snoozes included.
- `totals_by_kind(range)`: in the order of `AiUsageKind::ALL`, kinds without a call absent. `classify::budget_allows` should sum every kind but `NofapVision` from it; the vision cap reads `NofapVision` alone. `MemoryUsageRepo` has the same method with the same order.
- `delete_for_block(block_id)` returns the deleted rows (unlink their files) and clears `blocks.screenshot_id`. **Persist the scrubbed block first, or with `screenshot_id: None`**: a later `update` of a block that still carries the old id would write the pointer back.
- `LlmExplicitDetector::new(client)` takes the routing client. `check(image, model)`:
  - `Ok(check)` with `refused: false` for an answer that was read (any of the twelve combinations) and for one that could not be read (`UNSURE`);
  - `Ok(REFUSED)` (`unsure`, `low`, `refused: true`) for a refusal, in any of its forms: `stop_reason = refusal`, `message.refusal`, `finish_reason = content_filter`, or the HTTP 400 above;
  - `Err` for everything else: `AiNotConfigured` (no key, or no client for the selected provider), `AiRejected`, `RateLimited`, `Ai` (outage, two truncations), `Invalid` (blank model, empty image, a media type other than JPEG, PNG, WebP or GIF). Only `Ai` and `RateLimited` are `is_transient()`.
  - Pass the vision model of the provider in settings; a blank one is refused.
  - One check is at most two requests (the truncation retry), each with a 10 s timeout and the client's own retry policy on top. The 14 s bound of design 4.5 is the service's. A check cancelled by that bound after the vendor answered records no usage row, although it was billed.
- Usage: one `ai_usage` row per HTTP answer of kind `NofapVision` (so a retried truncation is two rows), with `at` at the start of the hour in UTC. A refused answer that came with a usage block is recorded; a 400 refusal is not (nothing was billed). In a time zone with a half-hour offset a check in the first half hour of a local month lands in the previous month's total.
- `FakeExplicitDetector`: `new()` (empty queue: a call fails with `CoreError::Ai`, so an unexpected check is noticed), `always(check)`, `push(Ok(..) | Err(..))`, `set_fallback(Some(check))`, `calls()`, `images()`, `models()`, and the helpers `FakeExplicitDetector::verdict(v, c)` and `::refusal()`. Queued answers come before the fallback.
- `ScriptedLlmClient::push_error(err)` queues a failure in script order; a failed call is still in `requests()`.
- **Logging, and the capture test of 11.2 (24).** `ubiqx-ai` writes nothing for a successful, refused or truncated `NofapVision` call. But the HTTP library under `reqwest` (`hyper_util`) writes `debug` and `trace` lines for every request of every kind ("connecting to …", "reuse idle connection for …", "pooling idle connection for …"), naming the provider's host and port. They say nothing about the kind or the answer, and they do grow with the number of checks. A capture test at `trace` has to leave lines of target `hyper_util` out of its count (as `tests/explicit.rs` does) or assert on content only.
- A failed check writes the retry loop's warn lines ("request failed", "retrying", "giving up after retries") with the vendor and the error text, and no kind.

**U7 and U8 (shells)**

- To keep the promise "no line per check at any level" for someone who raises the log level, the logger has to hold the target `hyper_util` (and, to be safe, `hyper`, `reqwest`, `rustls`) at `warn` or above, for example `level_for("hyper_util", LevelFilter::Warn)` on `tauri_plugin_log`. At the default `info` level nothing of it is written. In the standalone app this matters more, because the screen check is its only AI call: every such line is a check.
- **Never install a scoped `tracing` subscriber in an app** (`set_default`, `with_default`, `WithSubscriber`). The workspace builds `tracing` with its `log` feature, which forwards events to the `log` crate only while no dispatcher was ever set; the first scoped one switches that bridge off for the whole process and the log file goes quiet. That is why the clients skip their lines by kind instead of silencing a scope.
- Both products use the same migration list; a database opened by this build is at schema version 3.

**U9 (documents)**

- `services/ubi-api/README.md` now states the 4 MiB limit, the `413 request_too_large` answer and that a request body is forwarded as it came and never stored or logged. `PRIVACY.md` and the managed-route consent can rely on the last part: `tests/images.rs` checks the log and the ledger file.
- The desktop client reads the proxy's 413 as `CoreError::Invalid`. A reduced frame is some tens of kilobytes, far under the limit.

### Open points

- **The HTTP library's debug lines** (above) are outside what `ubiqx-ai` can silence without the side effect described. Someone has to set the logger's level for that target in both shells, and decide whether the design's sentence "logs nothing at any level" should be read as "this crate logs nothing".
- **The 400 refusal codes are unverified** against live APIs, and xAI's and Anthropic's ways of declining an image with an error status (if they have one) are not mapped. A provider that answers such a screen with another error makes the check return `Err`, which counts towards the service's backoff and writes a "request failed" warn line. Checklist item 11.4 (12) should include one explicit test image per provider and a look at the log.
- **`thinking: {"type": "disabled"}` on the managed route.** `thinking_disabled_for("ubi-fast")` is true, because the alias does not contain "haiku", so every request to the proxy carries the field although `ubi-fast` maps to a Haiku model, which the client's own comment says must not receive it. This is how every existing kind of call already behaves and the design prescribes the same function for the screen check, so I left it. Whether the vendor rejects it was not tested.
- **Real cost and image tokens per provider** are still estimates (design 4.7). The recorded cost uses the existing price table; for OpenAI and xAI it prices whatever token count the vendor reports.
- **`nofap_state.updated_at`** is the wall-clock time of the last save, like `settings.updated_at`. It is the time of a configuration change, not of an event, but the service saves the configuration for bookkeeping too (`last_help_at`, pending changes), so it moves more often than the user changes a setting. Nothing reads it.
- `MemoryNofapRepo` (the reference, in `ubiqx-engine`) does not have the stricter behaviours listed under deviations. Engine tests that run on it will not see an invalid day or a named learned site refused; `tests/nofap.rs` here covers those on SQLite.
